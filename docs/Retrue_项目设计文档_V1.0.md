# Retrue · 运动康复智能工作台项目设计文档

> **文档版本：** V1.0  
> **日期：** 2026-08-26  
> **项目名称：** Retrue  
> **产品定位：** 面向运动康复师的客户管理 + 康复记录 + AI 辅助工作台  
> **当前状态：** 核心需求基本确认，进入产品设计与技术落地阶段

---

## 1. 项目概述

### 1.1 产品定位

Retrue 是一套面向运动康复师 / 物理治疗师的智能工作台。

产品核心不是单纯“客户管理”，而是围绕康复师每天真实工作流程，解决以下问题：

- 今天有哪些客户、什么时候上课
- 新客户首次评估怎么快速记录
- 每次课前如何快速回顾上次情况
- 每次课后如何用自然语言快速完成记录
- AI 如何帮助整理动作、疼痛、观察和下次计划
- 康复过程如何按阶段持续推进
- 如何管理动作库、家庭训练、课时和回访事项
- 如何将长期训练记录沉淀成个人康复案例库

### 1.2 当前主要使用对象

V1 优先服务：

- 运动康复师
- 物理治疗师
- 当前先以单一康复师真实业务流程作为首个落地场景

未来支持：

- 多康复师账号
- 管理员
- 同事使用同一套系统
- 客户端 / 微信小程序分享能力

### 1.3 产品原则

1. **记录效率优先**：尽量减少表单填写，允许康复师使用自然语言和语音快速记录。
2. **AI 只生成草稿，不直接改正式数据**：AI 自动提取、归类、推荐后，关键数据必须由康复师确认。
3. **专业判断由康复师完成**：AI 只提供辅助建议，不替代专业诊断和最终治疗决策。
4. **历史数据可追溯**：正式记录修改必须留下审计记录和修改原因。
5. **业务流程优先于功能堆积**：V1 优先跑通“课前 → 训练 → 课后记录 → 下次备课”的闭环。
6. **先单体、后扩展**：系统优先保持简单，未来再按真实需求扩展 RAG、异步任务、移动端和多人协作。

## 2. V1 核心业务闭环

```text
课表 / 今日安排
        ↓
今日客户
        ↓
进入客户档案
        ↓
课前备课
        ↓
康复训练
        ↓
课后自然语言 / 语音记录
        ↓
AI 自动结构化整理
        ↓
康复师确认 / 修改
        ↓
正式保存
        ↓
更新时间线 / 康复进展 / 下一步计划
        ↓
下一次备课
```

首次评估、康复计划、复评、动作库、家庭训练、课时和回访事项均围绕该主流程服务。

## 3. 功能模块

### 3.1 首页 / 今日工作台

首页主要回答三个问题：

1. 今天有哪些客户？
2. 现在有哪些事情需要处理？
3. 如何快速开始记录？

#### PC 首页

主要展示：

- 今日日期
- 今日课程数量
- 待回访数量
- AI 待确认记录数量
- 今日课程
- 待处理事项
- 快捷入口
- 最近客户
- AI 待确认记录

#### 手机 / 小程序首页

仅保留高频内容：

- 今日课程前三条
- 待处理
- 统一补记
- 新客户

手机端不直接压缩 PC 页面，而采用任务式导航。

## 4. 客户管理

### 4.1 客户基础信息

| 字段 | 说明 |
| --- | --- |
| customerId | 系统内部唯一编号 |
| 姓名 | 客户姓名 |
| 手机号 | 可修改，不直接作为数据库主键 |
| 手机号脱敏值 | 列表默认显示，如 `138****1234` |
| 性别 | 可选 |
| 年龄 / 出生日期 | 可选 |
| 职业 | 可选 |
| 运动项目 | 可选 |
| 主要问题 | 当前主要康复问题 |
| 受伤日期 | 可选 |
| 手术日期 | 特殊情况使用 |
| 主负责康复师 | V1 一人负责 |
| 状态 | 正常 / 暂停 / 结案 |
| 首次到店日期 | 自动或手动记录 |
| 代课备注 | 未来替课场景预留 |

### 4.2 手机号规则

- 客户列表默认脱敏
- 只有进入客户资料编辑场景才显示完整手机号
- 康复师允许修改手机号
- 系统使用 `customerId` 建立内部关联，避免手机号变化造成历史数据失联

## 5. 首次评估与阶段复评

### 5.1 新客户必问项

每位新客户首次评估必须包含以下 7 类问题：

1. 哪里不舒服？
2. 什么时候开始的？
3. 怎么开始的：受伤 / 突然发作 / 慢慢加重？
4. 什么情况下会加重或减轻？
5. 之前有没有看过医生 / 做过什么治疗？
6. 平时运动习惯 / 工作性质？
7. 这次来的目标是什么？

### 5.2 特殊情况追加

根据客户情况再询问：

- 既往手术史
- 用药情况
- 睡眠情况
- 压力情况

### 5.3 评估内容

支持：

- 主诉
- 病史
- 康复目标
- 疼痛
- 关节活动度
- 肌力
- 特殊测试
- 标志点
- 围度
- 功能动作
- 自由备注

### 5.4 阶段复评

康复过程中可随时新增复评。

复评不能覆盖首次评估，每次单独保存：

- 日期
- 当前状态
- 疼痛变化
- 活动度变化
- 力量变化
- 功能变化
- 阶段进展参考
- 是否需要调整康复计划

## 6. 疼痛记录标准

疼痛采用 **0～10 分数字评分**。

建议统一产品术语为：

**NRS（Numeric Rating Scale）0–10**

### 6.1 标准字段

| 字段 | 示例 |
| --- | --- |
| 评分 | 6 / 10 |
| 部位 | 左膝前侧 |
| 诱发动作 | 下蹲至 90° |
| 疼痛类型 | 刺痛 / 酸胀 |
| 时间维度 | 训练前 / 训练后 |
| 场景 | 静止 / 动作时 |

示例：

> 左膝前侧刺痛，NRS 6/10，下蹲至 90° 时加重，静止不痛。

AI 应尽可能从自然语言中自动提取以上信息。

---

## 7. 力量记录

### 7.1 主要记录方式

以 **0～5 级肌力分级**作为标准字段。

### 7.2 辅助信息

允许补充：

- 抗阻次数
- 训练重量
- 左右差异
- 自由文本描述

系统采用：

> 标准化字段 + 自由文本

而不是强制所有数据必须结构化。

## 8. 康复计划与阶段管理

### 8.1 默认四阶段框架

系统提供默认模板：

1. 急性期 / 疼痛控制
2. 恢复期 / 活动度恢复
3. 力量重建期
4. 功能回归期

### 8.2 设计原则

- 不强制所有客户从第一阶段开始
- 允许直接进入力量重建期
- 允许某客户长期停留在某阶段
- 术后客户可以严格按阶段推进
- 康复师可手动修改阶段

### 8.3 AI 阶段进展提示

阶段推进没有固定统一指标。

AI 自动从历史记录中提取：

- 疼痛是否明显减轻
- 活动度是否改善
- 肌力是否进步
- 功能动作是否提高
- 客户主观反馈是否改善

生成：

> **阶段进展参考**

例如：

```text
阶段进展参考

最近3次记录显示：
- 下蹲疼痛由 NRS 6 降至 NRS 2
- 膝关节屈曲活动度改善
- 单腿蹲稳定性提高

系统判断：当前存在进入下一阶段的迹象。

[继续当前阶段]
[确认进入下一阶段]
```

**AI 不允许自动改变康复阶段。**

## 9. 课前备课助手

进入客户档案后，可点击：

**备课**

系统自动汇总：

- 上次训练做了什么
- 上次客户反馈
- 康复师上次观察
- 当前疼痛
- 关键指标变化
- 当前康复阶段
- 上一次“下次计划”
- 历史注意事项
- 风险信息

AI 再给出：

- 建议重点检查的内容
- 推荐特殊测试
- 推荐检查部位
- 本次训练思路
- 可能的问题方向
- 风险提醒

## 10. 每节课训练记录

每节课最重要的 5 类信息：

1. **动作**
2. **组数 / 次数 / 负荷**
3. **客户感受**
4. **康复师观察**
5. **下次计划方向**

### 10.1 示例

康复师输入：

> 今天做了臀桥 3 组 12 次，靠墙静蹲 3 组 30 秒。左膝下蹲还有一点疼，大概 2 分，但是比上次稳定。下次可以开始加一些单腿稳定训练。

AI 整理为：

```text
动作
- 臀桥：3 × 12
- 靠墙静蹲：3 × 30 秒

客户感受
- 左膝下蹲时疼痛 NRS 2

康复师观察
- 稳定性较上次改善

下一步计划
- 增加单腿稳定训练
```

## 11. AI 草稿确认机制

所有 AI 自动写入场景统一遵循：

```text
用户原始输入
      ↓
AI 解析
      ↓
结构化草稿
      ↓
用户确认 / 修改
      ↓
正式保存
```

### 11.1 需要人工确认的场景

包括：

- 多客户统一补记
- 客户姓名识别
- 疼痛提取
- 动作识别
- 训练量提取
- 观察提取
- 下一步计划
- 首次评估自动整理
- 复评自动整理

### 11.2 客户识别不确定时

例如：

> 老王今天膝盖还是疼。

系统存在多个“王姓”客户时：

> 你说的是哪位客户？

显示候选客户，让康复师选择。

不允许猜测后直接保存。

## 12. 历史记录与审计

### 12.1 历史正式记录不允许 AI 自动修改

如果发现历史记录错误：

- 必须由人工发起修改
- 填写修改原因
- 保存修改前数据
- 保存修改后数据
- 保存操作人
- 保存修改时间

### 12.2 AI 与人工数据

建议至少保留：

1. 用户原始输入
2. AI 初始解析结果
3. 最终确认结果
4. 后续修改记录

## 13. 时间线与个人案例库

每个客户拥有完整时间线：

```text
首次评估
   ↓
第1次训练
   ↓
第2次训练
   ↓
阶段复评
   ↓
康复阶段调整
   ↓
后续训练
   ↓
结案
```

### 个人康复案例库

不额外复制一套案例数据。

系统直接基于：

- 客户档案
- 首次评估
- 复评
- 康复计划
- 每次训练记录

形成可搜索的个人案例库。

### 13.1 客户私有康复知识库与 AI 记忆

客户档案不仅是业务记录的集合，也是辅助康复师判断的**客户私有知识库**。它与通用康复专业知识库分层建设：

```text
通用专业知识库：动作、测试、红旗信息、康复原则
                 ↓（只读参考）
客户私有知识库：该客户的确认事实、历史摘要、风险与偏好
                 ↓（按客户严格隔离）
AI 助手 / 备课助手 / 风险分析
```

#### 客户知识内容

客户私有知识库优先保存经康复师确认的高价值信息：

- 医疗与康复背景：诊断或转诊信息、手术/受伤史、既往治疗、用药和检查结论。
- 安全限制：红旗风险、禁忌动作、疼痛诱发因素、负荷限制、需要转诊或复查的条件。
- 康复过程：当前目标、阶段结论、有效或无效的训练策略、关键指标变化。
- 个体化偏好：沟通方式、训练依从性、时间安排、器械条件和家庭训练限制。
- AI 对话记忆：与该客户相关、且被康复师确认有长期价值的结论摘要；不把整段自由对话直接当作事实。

每条知识均需带有分类、内容、来源、重要级别、生效状态、创建/更新人和时间。风险或禁忌信息应支持置顶，并在 AI 上下文中优先呈现。

#### 写入与确认规则

1. 康复师可在客户详情中手动新增、修改、停用知识条目。
2. AI 可从训练记录、评估或对话中**建议**候选记忆，但不得自动写入客户知识库。
3. 候选记忆必须展示来源和拟写入内容，由康复师确认后才成为正式知识。
4. 正式知识的修改、停用和删除必须保留审计记录；历史训练/评估原文不因知识摘要更新而被覆盖。
5. 客户结案后默认保留知识用于历史追溯；再次启用时由康复师复核仍有效的安全限制。

#### AI 查询与会话记忆

AI 助手可处于两种模式：

- **通用模式**：未选择客户，仅检索通用专业知识，不携带任何客户健康信息。
- **客户模式**：明确选择客户，或从客户详情页自动绑定当前客户。请求只携带该客户的有效知识、当前阶段、近期训练/评估摘要、未处理风险以及同一客户最近会话摘要。

对话记录按“康复师 + 客户”隔离。为控制上下文长度，AI 每轮读取最近若干轮对话和经确认的会话摘要；摘要也必须可查看、编辑、停用。不同客户、不同康复师之间严禁共享对话或记忆。

AI 回答必须说明当前是否正在使用客户上下文；未绑定客户时不得暗示已了解客户病史。AI 仍只提供辅助建议，不做诊断、不自动修改正式业务数据。

## 14. 家庭训练模块

康复师可在课后创建家庭训练计划。

包含：

- 动作
- 组数
- 次数
- 频率
- 注意事项
- 图片（后续）
- 视频（后续）
- 示范说明（后续）

AI 可以自动整理成客户版文案。

例如：

```text
今天回家可以做：

1. 臀桥
3组 × 12次

2. 靠墙静蹲
3组 × 30秒

注意：
如果训练过程中膝盖疼痛明显增加，请先停止训练。
```

支持：

**一键复制文本，发送给客户。**

客户端 / 小程序展示能力作为后续扩展。

## 16. 课时管理

### 16.1 课程时长

系统不写死 30 / 60 分钟。

允许：

- 30 分钟
- 45 分钟
- 60 分钟
- 90 分钟
- 自定义时长

并单独记录：

**课时消耗量**

### 16.2 课时消耗节点

必须满足：

```text
课程已经完成
+
本次训练记录已经确认保存
```

之后才正式消耗课时。

### 16.3 特殊情况

- 请假：不扣
- 取消：不扣
- 补课：不重复额外扣除
- 人工调整：必须填写原因

### 16.4 剩余课时

当前课表存在：

- 上剩一
- 上剩二

等备注。

课时同步逻辑暂不完全锁定，后续专项设计。

## 17. 课程体系、课表与导入

### 17.1 课程语义分层

系统必须区分“课程类型”“客户疗程”“课程排期”和“训练记录”，避免把日历中的一节课误当作可复用课程。

```text
课程类型 CourseType（康复师维护的课程目录）
        ↓
客户疗程 CustomerCourse（分配给某客户、某康复周期的实际疗程）
        ↓
课程排期 CourseSession（日历中某天某时的一节课）
        ↓
训练记录 TrainingRecord（该节课实际完成的训练内容）
```

示例：

```text
课程类型：膝关节术后力量重建疗程
客户疗程：张三的膝关节术后力量重建疗程（第 2 周）
课程排期：2026-09-01 14:00-15:00
本节训练主题：单腿稳定性与臀肌激活
训练记录：实际动作、训练量、客户感受与康复师观察
```

#### 课程类型 CourseType

课程类型相当于“高数课/经济学课”这一层：由康复师维护、可复用、可分配给不同客户的课程定义，而不是某次具体上课记录。

字段建议：

- 所属康复师、名称、简介和启用状态；未来可支持官方模板与个人副本。
- 默认时长、默认课时消耗量、默认适用康复阶段。
- 默认课程目标、注意事项、推荐动作或评估项。
- 创建/更新信息；已被客户疗程引用的类型不得物理删除，只能停用。

#### 客户疗程 CustomerCourse

客户疗程是将课程类型分配给一位客户后形成的个体化执行单元。一个客户可以在不同时间拥有多个疗程，也可以在同一康复计划内并行多个疗程。

字段建议：

- 客户、课程类型、可选关联康复计划/阶段。
- 实际开始/结束日期、状态（待开始 / 进行中 / 暂停 / 已完成 / 已取消）。
- 个体化目标、计划课次或计划课时、默认时长和默认消耗量的快照与调整说明。
- 可选关联课时包；若一个课时包支持多个疗程，具体扣减需在课程排期层记录来源。

课程类型后续被编辑时，不应改变已经开设的客户疗程快照，避免历史疗程含义漂移。

#### 课程排期 CourseSession

课程排期是日历中的实际预约条目。新建排期的标准流程为：先选择客户，再选择该客户“进行中”的客户疗程，最后填写时间和本节训练主题。

- 每个排期只关联一个客户和一个客户疗程；其客户必须与客户疗程的客户一致。
- 日期、开始/结束时间、状态、备注属于排期；同一日期可有多位客户、多节课程。
- **本节训练主题**仅描述本次课内容，例如“单腿稳定性与臀肌激活”，不等于课程类型。
- 已完成课程必须关联已确认训练记录，才允许触发对应课时包的扣减；取消和请假不扣。
- 服务端负责校验开始/结束时间、客户/疗程归属和状态转换；后续增加可配置的排班冲突提醒。

#### 课时包 CoursePackage

课时包是客户的收费权益与余额，不是课程类型，也不等同于客户疗程。它记录购买/调整/消耗的次数或单位；课程排期完成后按其关联客户疗程的规则扣减，并保留扣减来源。

若需要支持“半课/全课”，课时包和排期消耗量应统一使用可表示 `0.5`、`1.0` 的课时单位，而不是只使用整数课次。

当前真实课表：

- 在线 Excel
- 行 = 康复师
- 列 = 7:00～20:00 时间段
- 单元格 = 客户姓名 + 课时标注
- `*2` = 全课
- 无标注 = 半课
- 可能存在拍摄 / 跟课 / 直播等非客户事项

当前属于定制化场景。

### 17.2 当前实现与过渡策略

暂不阻塞核心系统开发。

系统提供手动排课作为 V1 的正式能力：

- 使用月历展示当前康复师自己的课程。
- 点击日期或“新增课程”可创建课程。
- 排课时必须选择本人名下客户，并填写日期；开始/结束时间与备注可选。
- 当前 `course_name` 仅作为“本节训练主题”的过渡字段，用于描述该次课程内容；它不是课程类型。
- 课程可后续修改客户、日期、时间、备注和状态（待上课 / 已完成 / 已取消 / 请假）；取消课程保留历史，不直接删除。
- 课程状态默认“待上课”，不自动扣除课时。
- V1 暂不做课程时间冲突校验；康复师可根据月历自行安排。

在实现上述分层模型前，不应再将 `course_name` 扩展为课程目录或课时扣减依据。迁移时保留历史排期，将其现有 `course_name` 迁入 `session_topic`；历史记录由康复师逐步关联客户疗程，禁止未经确认自动推断课程类型。

系统同时保留：

**导入课表**

入口。

后续拿真实 Excel 文件做专项解析设计。

## 20. 风险提醒

AI 检测到异常情况时，可以明确提醒。

例如：

> ⚠️ 风险提醒：客户下蹲时左膝反复刺痛，NRS 6/10，连续 3 次未明显改善。建议暂停当前高负荷训练并进一步评估，必要时考虑转诊。

### 20.1 风险信息建议结构化保存

| 字段 | 说明 |
| --- | --- |
| 风险等级 | 低 / 中 / 高 |
| 发现依据 | AI 根据哪些历史信息判断 |
| 建议动作 | 暂停 / 复查 / 检查 / 考虑转诊 |
| 是否确认 | 康复师是否确认 |
| 处理结果 | 康复师最终处理方式 |

### AI 边界

AI 可以：

- 提醒
- 推荐检查
- 建议暂停某项训练
- 建议进一步医学检查
- 提示考虑转诊

AI 不负责最终医学诊断。

## 32. 双层知识库与 RAG 设计方向

V1 先使用通用模型与直接数据库查询；后续逐步建设通用专业知识库和客户私有康复知识库。

知识范围可能包括：

- 特殊测试
- 测试操作方法
- 阳性意义
- 康复评估知识
- 风险 / 红旗信息
- 动作说明
- 禁忌信息
- 康复师自有专业资料

客户私有知识库范围见 13.1，包含经确认的安全限制、康复过程结论、偏好和会话摘要。它不是面向所有客户的案例库，任何检索必须先以 `therapist_id + customer_id` 过滤。

技术方案：

```text
Django
  ↓
AI Context Builder（权限校验、客户上下文摘要）
  ├── 直接查询 PostgreSQL 业务数据（阶段、风险、近期记录）
  ├── 客户私有 Retriever（therapist_id + customer_id 强制过滤）
  └── 通用专业 Retriever（动作库 / pgvector）
  ↓
LLM
```

客户历史业务数据仍直接查询数据库，不需要全部转成 RAG 文档。只有经确认、适合长期复用的客户知识和会话摘要可异步生成向量；向量索引只用于召回，最终权限控制始终在业务数据库查询层执行。
