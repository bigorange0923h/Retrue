# 客户身份解析与客户目录匹配调整方案

> 状态：待实施  
> 适用范围：统一 AI 助理中的训练补记、评估、随访、训练修订、客户查询与客户历史咨询。  
> 目标：以当前康复师名下的客户目录匹配原文，而非以“2～4 个汉字”的正则猜测姓名。

## 1. 背景与问题

当前编排器会用正则从“张三今天做了……”等原文提取姓名提示。该规则只适合作为临时兜底，不能承担身份识别：姓名长度、别称、英文名、称呼和自然语言位置都会造成漏匹配或误匹配。多客户补记还会依赖同类规则判断人数与顺序。

客户身份必须由当前登录康复师的客户目录决定；模型或正则都不能把文本片段直接当作客户身份，更不能跨康复师查询。

## 2. 总体原则

```text
先识别是否需要客户上下文
  ├─ 否：不读取客户目录，直接处理通用任务
  └─ 是：仅读取当前康复师的最小客户目录
       → 在原文中做受控匹配
       → 单一匹配：预选该客户并继续
       → 多个/歧义匹配：展示候选，由康复师选择
       → 无匹配：要求补充姓名或打开受控搜索
```

- 仅客户相关任务加载客户目录；“臀桥怎么做”等通用知识咨询不访问任何客户数据。
- 查询范围恒为 `Customer.objects.filter(therapist=request.user)`；客户端不能传入康复师或任意客户目录。
- 原文匹配只能得到“预选/候选”，不等同于正式业务写入确认。训练、评估、随访等仍必须经过草稿与最终确认。
- 不把完整客户目录、原始手机号或原文写入持久化 Graph State；页面恢复时重新在服务端按当前权限加载目录并重新匹配。

## 3. 客户相关任务判定

在意图初筛后增加 `requires_customer_context`，而不是一开始就加载客户目录。

| 场景 | 是否加载目录 | 示例 |
| --- | --- | --- |
| 通用知识 | 否 | “臀桥怎么做？” |
| 训练补记 | 是 | “黄伟成今天做了三组臀桥” |
| 评估、随访、训练修订 | 是 | “给阳峥嵘做复评” |
| 客户查询/历史咨询 | 是 | “张三做了几次训练？”、“王五上了几次课？” |
| 风险问题 | 默认否；只有明确指向客户且后续需读取客户事实时才是 | “红肿发热怎么办？” / “张三红肿发热怎么办？” |

对于“张三做了几次训练？”这类未预先绑定客户的咨询，先按“客户历史咨询候选”处理：加载目录、匹配身份；匹配完成后才执行训练记录、课程、评估等只读 Tool。不能因为尚未绑定客户就退化为通用回答。

## 4. 客户目录与别称

### 4.1 目录最小字段

新增受控领域服务 `load_therapist_customer_directory(therapist)`，仅返回：

```json
[
  {
    "id": 35,
    "name": "黄伟成",
    "aliases": ["阿成"],
    "phone_masked": "138****1234"
  }
]
```

- `id` 用于后续权限复核和选择提交。
- `name` 与 `aliases` 用于文本匹配。
- `phone_masked` 只用于候选卡区分同名客户，不作为模型输入；不得返回完整手机号。
- 当前 `Customer` 模型尚无客户别称字段。实施时应新增独立 `CustomerAlias` 表（建议字段：`customer`、`alias`、`normalized_alias`），并约束同一康复师范围内别称唯一或在冲突时标记歧义；不能假设现有动作别名表可复用。

### 4.2 内存 State 与持久化边界

Graph State 可以在**单次运行内存**中拥有 `customer_directory` 和 `customer_matches`：

```python
customer_directory: list[CustomerDirectoryEntry]  # 仅当轮内存
customer_matches: list[CustomerMatch]             # 仅当轮内存
```

其中 `CustomerDirectoryEntry` 只含上表字段；`CustomerMatch` 至少含 `customer_id`、`matched_alias`、`start_offset`、`end_offset`、`confidence`。

它们不得加入 `PERSISTED_STATE_KEYS`，也不得写进 `AssistantTask.state_data`、Graph checkpoint、TaskEvent 或模型提示词。等待/恢复只持久化最小引用：

```json
{
  "customer_id": 35,
  "identity_resolution": {
    "status": "preselected | waiting_selection | unresolved",
    "matched_customer_ids": [35],
    "source": "directory_exact"
  }
}
```

恢复任务时再次调用目录服务、按当前客户归属重新校验；若客户已被停用、转移或删除，清空预选并进入重新选择，不能信任历史缓存。

## 5. 匹配算法

匹配应是确定性、可解释的领域逻辑，不依赖模型猜姓名。

1. 对原文、姓名和别称做统一规范化：Unicode NFKC、去首尾空白、统一英文字母大小写、移除“客户/病人/患者”等称呼与不影响姓名的分隔符。
2. 为当前康复师每位客户生成名称键：正式姓名 + 已启用别称；空键不参与匹配。
3. 在规范化原文中匹配名称键；同起始位置优先最长名称，生成不重叠、按原文位置排序的匹配结果。
4. 同一名称键映射多个客户、短名称被长名称包含、或同一片段有冲突时，标为 `ambiguous`，不得自动绑定。
5. 单一精确命中标为 `exact`；仅在已判定为客户相关任务时允许预选。模糊匹配（拼音、编辑距离、只匹配姓氏）只可用于搜索排序，永不自动绑定。
6. 可选支持用户输入的手机号后四位匹配；只比对服务端计算的后四位，不将完整手机号放入 State 或提示词。

正则仍可保留在“识别训练语义、分句、寻找时间/动作/数量”的层面；不再用于决定客户姓名或客户数量。

## 6. 单客户流程

```text
客户相关意图
  → load_therapist_customer_directory
  → match_customers_in_text
  ├─ exact 且仅一位客户
  │    → customer_preselected 卡片（显示姓名、脱敏电话、可更换）
  │    → 训练：生成 pending 草稿
  │    → 咨询：执行受控只读 Tool 后回答
  ├─ ambiguous / 多候选
  │    → customer_selection 卡片，等待选择
  └─ 无匹配
       → 提示补充完整姓名
       → 提供“搜索客户”入口（服务端按关键字、当前康复师范围检索）
```

`customer_preselected` 是“系统已从原文精确识别”的可见卡片，不是静默绑定：页面应展示当前处理客户，并提供“更换客户”。在训练、评估等写入类流程中，正式记录仍由“确认并保存”按钮提交；在只读咨询中，精确预选后才允许读取该客户事实。

无匹配时不应一次性向前端展示该康复师所有客户。默认提示用户补充姓名；“搜索客户”由用户主动触发，并分页返回最少必要候选资料。

## 7. 多客户训练补记

多客户流程不再靠“两个 2～4 字片段”识别客户数。先按训练语义将原文拆成候选记录段，再对每一段运行同一目录匹配算法。

```text
原文记录段（保留原文顺序）
  → 段 1：目录匹配 → 预选 / 等待选择 / 等待补充
  → 段 2：目录匹配 → 预选 / 等待选择 / 等待补充
  → …
  → 创建顺序固定的批量子项
  → 从第 1 项依次生成草稿、确认、保存，再推进下一项
```

- `TrainingRecordBatchItem.sequence` 以原文记录段的位置为准，不能按客户目录顺序或匹配完成时间排序。
- 每个子项独立保存 `customer_id`（已预选时）或身份解析状态；不得把第一个匹配客户套用到后续子项。
- 即使后续项已精确匹配，也只显示当前项，上一项正式确认/跳过后才推进；保持现有串行写入和幂等约束。
- 某段无匹配或歧义时，仅暂停该段；康复师解决后从该段继续，不能重排或重新处理已完成子项。

## 8. Graph 节点与接口调整

建议增加以下节点与领域服务：

```text
classify_intent
  → needs_customer_context?
  → load_customer_directory
  → resolve_customers_from_text
  ├─ single_customer_flow
  ├─ customer_question_flow
  └─ multi_customer_split_and_resolution
```

建议节点职责：

| 节点/服务 | 责任 |
| --- | --- |
| `requires_customer_context` | 根据受控意图决定是否读取目录 |
| `load_customer_directory` | 仅加载当前康复师范围的最小资料，运行期内存缓存 |
| `resolve_customers_from_text` | 规范化、精确匹配、冲突检测、原文排序 |
| `wait_customer_selection` | 展示歧义候选并等待客户 ID |
| `wait_customer_name` | 无匹配时等待补充文本或主动搜索 |
| `submit_customer_selection` | 再次校验客户归属后，按既有意图定向恢复 |

接口层不接受客户端上传的客户目录或匹配结果。前端仅提交 `customer_id` 和明确的“更换/选择”动作；服务端重新校验该 ID 归属当前康复师。

## 9. 前端交互

| 身份结果 | 卡片文案 | 可用操作 |
| --- | --- | --- |
| 单一精确匹配 | “已识别当前客户：黄伟成” | 更换客户；继续后续流程 |
| 多候选/歧义 | “请选择客户” | 选择候选；搜索；取消 |
| 无匹配 | “未找到匹配客户” | 补充姓名；搜索客户；取消 |
| 多客户子项 | “第 2/3 位客户：已识别为阳峥嵘” | 更换；完成上一项后继续 |

候选卡只显示姓名、别称命中提示和脱敏手机号；不显示病史、完整电话、训练历史或其他客户的业务资料。

## 10. 验收用例

1. “黄伟成今天做了三组臀桥，每组 10 次”精确预选黄伟成，草稿为臀桥 3 × 10。
2. “张三做了几次训练？”在张三唯一命中时读取且只读取张三的训练记录。
3. “王五上了几次课？”在王五唯一命中时读取且只读取王五的课程记录。
4. 同一康复师有两位“张三”或别称冲突时，必须展示候选，不自动读取或写入。
5. 当前康复师名下不存在原文姓名时，提示补充/搜索，不查询其他康复师客户。
6. “臀桥怎么做？”不加载客户目录、无客户 ToolExecution。
7. 多客户原文按提及顺序生成子项；已完成第 1 项后才处理第 2 项。
8. 暂停后恢复时重新加载当前康复师目录；客户被删除或不再归属时不沿用旧预选。
9. Task state、事件、Run 摘要和日志中不出现完整手机号、客户目录列表或原始对话。

## 11. 迁移步骤

1. 新增客户别称模型、管理/维护入口、唯一性与归属约束。
2. 新增客户目录服务及单位测试，确保只返回最小脱敏字段。
3. 实现文本规范化、精确匹配、冲突检测和按原文排序；替换姓名正则作为身份来源的现有分支。
4. 将单客户训练、客户咨询、评估/随访/修订接入身份解析节点。
5. 将多客户拆分改为“先分段、再目录匹配”，保留现有子项状态机与串行保存。
6. 增加预选、歧义、无匹配和搜索卡片；保留“更换客户”。
7. 覆盖第 10 节验收用例，并以 `AI_ORCHESTRATION_ENABLED` 作为可回滚开关逐步启用。
