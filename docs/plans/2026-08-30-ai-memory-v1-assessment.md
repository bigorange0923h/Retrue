# AI 长期记忆 V1 落地评估

## 已落实

- 在现有客户知识库上扩展长期记忆，不新建平行数据源。
- 实现结构化记忆类型、标准化值、置信度、重要度、来源定位、确认时间和生命周期。
- 候选确认先去重；需要替代时必须由康复师显式确认。
- 删除与停用改为保留历史的生命周期操作，并写审计日志。
- 备课助手仅带入最多 10 条 `active` 记忆，且标注为 `MEMORY`，不与训练、评估等正式事实混淆。
- 所有 AI 入口共用 Conversation/Message，会话记录康复师、可选客户、入口和关联业务资源。
- 客户会话每轮完成后执行结构化记忆评估，只生成候选，不直接写入长期记忆。
- 同一客户、同一 `memory_key` 的不同内容会关联旧记忆并提示冲突，由康复师选择替代、保留、条件并存或暂缓。
- 每段会话上下文保留最近 10 条原始消息；更早消息增量合并为滚动摘要，完整消息仍保留用于追溯。
- 长对话每累计 10 条压缩消息评估一次 Memory Episode；Episode 先进入候选，确认后最多 3 条进入客户上下文。

## 设计取舍

当前项目已有 `CustomerKnowledgeItem` 和 `KnowledgeCandidate`，因此 V1 复用它们作为 `customer_memory` 的实现载体，保持 API 与已存数据兼容。结构化短记忆不做向量检索；现有 embedding 能力仅继续服务于 RAG。该取舍符合“PostgreSQL 是事实源、Memory 不等于 RAG”的原则。

## 下一阶段前置条件

1. 为 Episode 增加 embedding 和按当前问题的语义检索；当前 V1 按重要度和时间读取。
2. 将更多训练、评估、计划事实接入统一 Context Builder，并按 token 预算裁剪。
3. 增加康复师个人 Memory（仅 therapist_id），与“康复师对客户的观察”严格区分。
4. 制定客户彻底删除时对会话、记忆、向量的同事务或队列清理流程。
